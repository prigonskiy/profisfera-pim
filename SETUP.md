# PIM — настройка и запуск

Django-проект PIM. Готовы все 5 этапов: модель данных, админка, динамические
категорийные характеристики с транслитерацией, JSON-API каталога и деплой на VPS.

## Локальный запуск

Нужен Python 3.12+. На Windows — официальный установщик с python.org с
включённой галочкой «Add python.exe to PATH».

```bash
# 1. Создать виртуальное окружение
python -m venv venv          # macOS/Linux: может быть python3

# 2. Активировать его
source venv/Scripts/activate   # Windows (Git Bash)
# source venv/bin/activate     # macOS / Linux

# 3. Поставить зависимости (python -m pip надёжнее, чем просто pip)
python -m pip install -r requirements.txt

# 4. Создать таблицы базы данных
python manage.py migrate

# 5. Создать учётную запись администратора
python manage.py createsuperuser

# 6. Запустить сервер
python manage.py runserver
```

После активации в начале строки терминала появляется `(venv)`. В каждом новом
окне терминала окружение нужно активировать заново (шаг 2). На Windows команда
называется `python` (не `python3`).

Открыть http://127.0.0.1:8000/admin/ — теперь там полноценная админка:
бренды, категории, характеристики, документы и карточки товаров.

> **Обновляетесь с этапа 1?** После `git pull` обязательно повторите
> `pip install -r requirements.txt` — сменилась версия Django (на 5.2 LTS) и
> добавились пакеты редактора и сортировки. Новых миграций модели нет.

## Что умеет админка (этап 2)

- **Товар** — все блоки: изображения через галерейный виджет (загрузка пачкой,
  превью сразу после выбора, изменение порядка перетаскиванием мышью), краткое
  описание, полное описание в визуальном редакторе (TinyMCE), логистика,
  организационный блок, привязка готовых документов. Поле `alt` галерея не
  редактирует — оно автоматически заполняется названием товара при загрузке.
- **Категории** — с выбором родителя (вложенность).
- **Характеристики** — тип, единица, привязка к категориям, варианты значений
  (для списков) с сортировкой.
- **Бренды**, **документы** (загрузка PDF) — CRUD.

Блок категорийных характеристик в карточке товара появится на этапе 3
(нужна форма, зависящая от выбранной категории).

## Категорийные характеристики (этап 3)

В карточке товара появляется блок «Категорийные характеристики» с полями
ровно тех характеристик, что привязаны к категории товара — у каждой свой
виджет: выпадающий список, множественный выбор, число, текст или флажок.

Важный момент по порядку действий для **нового** товара: форма должна знать
категорию, чтобы понять, какие характеристики показать. Поэтому:

1. Создаёте товар, выбираете категорию, заполняете основные поля.
2. Жмёте «Сохранить и продолжить редактирование».
3. После сохранения внизу появляется блок «Категорийные характеристики» —
   заполняете и сохраняете ещё раз.

У уже существующего товара блок виден сразу. Пустые значения не сохраняются
(если очистить поле и сохранить — значение удаляется из базы).

## Транслитерация слагов

Поля `slug` (у товаров, категорий, брендов) и `code` (у характеристик) можно
оставлять пустыми — при сохранении они генерируются из названия
транслитерацией кириллицы в латиницу (Дрель ударная → `drel-udarnaia`).
## JSON-API каталога (этап 4)

API смонтирован на `/api/`. Корень сайта (`/`) перенаправляет туда, открыв
браузерный интерфейс DRF.

Эндпоинты (чтение — публичное, без авторизации):

- `GET /api/products/` — список товаров (постраничный, по 20).
  Параметры: `?category=<id>` (включая подкатегории), `?brand=<id>`,
  `?search=<строка>`, `?ordering=name|created_at|updated_at`, `?page=<n>`.
- `GET /api/products/<slug>/` — полная карточка: описания, бренд, категория,
  логистика, изображения (по порядку), документы и категорийные
  характеристики с типизированными значениями.
- `GET /api/categories/` и `GET /api/categories/tree/` — категории и дерево.
- `GET /api/brands/`, `GET /api/characteristics/`, `GET /api/documents/`.

### Запись по токену

Изменяющие запросы (POST/PUT/PATCH/DELETE) разрешены только сотрудникам
(`is_staff`) по токену. Без авторизации — 401, авторизован без прав — 403.

Создать токен для пользователя:

```bash
python manage.py drf_create_token <логин>
```

Токен также можно создать в админке (раздел «Tokens»). Использование:

```bash
curl -X POST http://127.0.0.1:8000/api/products/ \
  -H "Authorization: Token ВАШ_ТОКЕН" \
  -H "Content-Type: application/json" \
  -d '{"name": "Новый товар", "category": 1}'
```

Запись товара покрывает постоянные поля, категорию, бренд и привязку
документов. Изображения и значения категорийных характеристик пока
управляются через админку.

## Интеграция с внешними системами

Полный контракт контента и открытые вопросы — в [INTEGRATION.md](../INTEGRATION.md).
Кратко:

Архитектура: PIM — headless-источник **контента** (описания, изображения,
характеристики, документы, группировки, обучение). Деньги, остатки и
пользователи в контракт интеграции не входят (коммерческий слой на паузе).

**Ключ сопоставления контента — внутренний `sku`** (стабилен, уникален, не
переиспользуется). Прежнее поле `external_id` удалено (миграция 0023); код ERP
продавца теперь живёт на торговых предложениях (`Offer.erp_code`) и относится к
коммерческому слою, а не к контенту.

Запросы для интеграции:

- `GET /api/products/by-sku/<sku>/` — полная карточка по ключу контента.
- `GET /api/products/?sku=<sku>` / `?sku__in=a,b,c` — выборка по одному/нескольким sku.
- `GET /api/products/?updated_since=<ISO-8601>` — только изменённые после момента
  (инкрементальная синхронизация). Дату нужно URL-кодировать; неверный формат
  даёт 400, а не молчаливую отдачу всего каталога.
- `GET /api/schema/` — OpenAPI 3; `GET /api/docs/` — Swagger UI (весь контракт).

Рекомендуемый паттерн для MVP — периодический pull с `updated_since`; вебхуки/
пуш и направление обмена согласуются с внешней платформой (см. INTEGRATION.md).

## Модель данных (кратко)

- **Brand** — бренд: название, slug, логотип, описание.
- **Category** — категория с вложенностью через `parent` (ссылка на себя).
- **Characteristic** — характеристика: 5 типов (single_select, multi_select,
  number, text, boolean), единица измерения, привязка к категориям (M2M),
  машинный `code` для API.
- **CharacteristicOption** — варианты значений для характеристик-списков.
- **Document** — PDF-документ с названием и номером; связь с товарами M2M.
- **Product** — карточка товара: описания (краткое + полное HTML),
  организационный блок (категория, бренд, артикул), логистика (брутто
  ширина/высота/глубина в мм, масса в кг), документы M2M.
- **ProductImage** — изображения товара с полем `order` (для порядка).
- **ProductAttributeValue** — значение категорийной характеристики у товара
  (EAV). Хранит значение в нужном столбце по типу характеристики; уникальность
  пары (товар, характеристика) гарантируется ограничением БД.

## Принятые решения (можно изменить позже)

- **Вложенность категорий** — на `django-mptt` (перешли с self-FK на этапе 6):
  быстрые запросы по дереву, порядок и переподчинение перетаскиванием в админке.
- **Фильтры-фасеты наследуются вниз по дереву**: эффективные фильтры категории =
  свои + унаследованные от родителей, потомок переопределяет предка по одной и
  той же характеристике (`Category.effective_filters`). Сами значения
  характеристик у товара привязываются по его категории.
- **БД по умолчанию — SQLite** для мгновенного старта; на VPS переключим на
  Postgres переменной `DB_ENGINE=postgres`.
