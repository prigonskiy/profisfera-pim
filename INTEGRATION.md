# Интеграция каталога ProfiSfera PIM с внешней платформой (Ensi)

Документ для бэкенд-специалиста, оценивающего интеграцию. Это **черновик
контракта с нашей стороны** плюс список **открытых вопросов**, которые нужно
согласовать. Финальную схему обмена (направление и формат) фиксируем после
ответов Ensi — здесь описано то, что уже готово и не зависит от их стороны.

## TL;DR

- PIM — **headless-источник товарного контента**. Отдаёт каталог по REST/JSON.
- Машиночитаемый контракт: **OpenAPI 3** на `GET /api/schema/`, Swagger UI на
  `GET /api/docs/`.
- **Ключ сопоставления контента — внутренний `sku`** (стабилен, уникален, не
  переиспользуется). Не `id`, не `erp_code`.
- Инкрементальная выборка — параметр `updated_since` (ISO-8601).
- В контракт **не входят** деньги, остатки и пользователи (см. «Границы»).

## Границы интеграции

**В скоупе (контент):** товары, категории (дерево), характеристики и их
значения, бренды, документы (РУ/декларации/ИФУ и т. п.), навигационные фасеты
(аудитории/направления), группировки вариантов, обучение (курсы/модули/слайды),
изображения.

**Вне скоупа (на паузе, отдельный слой):** торговые предложения (склады,
остатки, цены по каналам), клиенты витрины и юрлица, авторизация покупателей.
Единственный источник правды по остаткам/ценам — не PIM. Это совпадает с
сервисной моделью Ensi, где контент и стоки/цены — разные сервисы.

## Архитектурный принцип

Редактор → админка → БД → REST-API (чтение публичное, запись по токену staff).
Витрина `profisfera-shop` собирается в статику из этого API. PIM остаётся
единственным источником правды по каталогу; наружу ходит только JSON.

## Ключ сопоставления: `sku`

- Внутренний артикул PIM, поле `Product.sku` (строка, напр. `1000000001`).
- Присваивается автоматически из отдельного счётчика, **не переиспользуется**
  после удаления, **не меняется** после присвоения.
- Есть в каждом ответе API; по нему работают выборка и адресация карточки.
- Рекомендуется как сквозной идентификатор товара на стороне Ensi.

> `erp_code` (код в ERP продавца) относится к коммерческому слою и для
> сопоставления **контента** использоваться не должен — см. открытый вопрос №6.

## Модель контента (что отдаём)

- **Product** — карточка: описания (краткое + полное HTML), категория, бренд,
  артикулы (`sku` + артикул производителя), GTIN, ТН ВЭД, страна производства,
  логистика (габариты/вес брутто), изображения, документы (M2M), привязка к
  серии вариантов, навигационные фасеты.
- **Category** — дерево (django-mptt): произвольная вложенность, порядок и
  переподчинение в админке. Фильтры-фасеты **наследуются вниз** по дереву.
- **Characteristic / CharacteristicOption** — характеристики 5 типов
  (single/multi select, number, text, boolean), единица измерения, привязка к
  категориям, флаги «глобальная» и «показывать покупателю».
- **CategoryFilter** — как характеристика показывается фильтром в категории.
- **ProductAttributeValue** — значение характеристики у товара (EAV).
- **Brand**, **Document** (тип/номер/орган/сроки/бессрочность),
  **Audience/Direction** (навигационная таксономия «для кого / для чего»).
- **ProductGroup / GroupLevel** — группировка вариантов: товар входит в одну
  серию и один уровень серии (FK `Product.group_level`). Это **однозначная**
  группировка, а не многоосевая матрица (прежняя многоосевая схема
  `GroupLevelValue/ProductGroupValue` удалена в миграции 0019).
- **Course / CourseModule / Slide** — обучение: у курса свой набор товаров
  (M2M), модуль бывает слайдами/видео/лонгридом; отдаётся внутри карточки.

## API-контракт (готово)

База: `/api/`. Чтение — публичное (аноним). Запись (POST/PUT/PATCH/DELETE) —
только staff по токену/сессии (`IsStaffOrReadOnly`). Пагинация — 20/страница.
Троттлинг анонимных задаётся в `.env`. Полная спецификация — в OpenAPI.

**Товары**
- `GET /api/products/` — список. Фильтры (комбинируются по И):
  `category` (ID, включает потомков), `brand` (ID), `audience`, `direction`
  (slug'и через запятую, внутри — ИЛИ), `sku`, `sku__in`, `search`, `ordering`,
  `updated_since`.
- `GET /api/products/{slug}/` — карточка (адресуется и по `slug`, и по `sku`).
- `GET /api/products/by-sku/{sku}/` — карточка по ключу сопоставления контента.

**Справочники**
- `GET /api/categories/`, `GET /api/categories/tree/` (дерево целиком),
  `GET /api/categories/{slug}/filters/` (эффективные фасеты с учётом наследования).
- `GET /api/brands/`, `GET /api/characteristics/`, `GET /api/documents/`.
- `GET /api/audiences/`, `GET /api/audiences/menu/` (готовое дерево меню),
  `GET /api/directions/`.

**Схема**
- `GET /api/schema/` — OpenAPI 3 (YAML). `GET /api/docs/` — Swagger UI.

### Инкрементальная синхронизация

`GET /api/products/?updated_since=<ISO-8601>` возвращает только товары,
изменённые после момента (по `updated_at`). Дату нужно URL-кодировать;
некорректный формат даёт 400 (а не молчаливую отдачу всего каталога).
Рекомендованный паттерн для MVP — периодический pull. Вебхуки/пуш —
см. открытый вопрос №2.

### Медиа

Изображения и файлы документов отдаются **абсолютными URL** (при наличии
`request` в контексте). На проде медиа раздаёт nginx.

## Открытые вопросы к Ensi

1. **Топология.** У Ensi есть собственный PIM-сервис. Мы кормим его контентом
   (import в Ensi PIM) — или отдаём контент дальше по конвейеру, минуя их PIM?
   От этого зависит формат и «кто главный по контенту».
2. **Направление обмена.** Их коннектор делает **pull** из нашего API
   (`updated_since` уже готов) — или мы делаем **push** в их сервис/формат?
3. **Формат приёма.** Если push/import: их API импорта (эндпоинт, схема тела),
   либо файловый импорт (какой формат/структура), либо оба.
4. **Группировка вариантов.** Мы отдаём **явную** серию/уровни. Ensi PIM умеет
   склеивать варианты **по атрибутам** сам. Забирают нашу группировку как есть —
   или переклеивают по атрибутам (тогда нужны стабильные атрибуты «оси»)?
5. **Обучение.** Курсы/слайды — нетиповой для e-com контент. Ensi это забирает
   как есть, игнорирует, или для него нужна отдельная сущность/страницы?
6. **`erp_code` в публичном чтении.** Сейчас доступны `?external_id=` и
   `by-external-id/` по коду ERP продавца. Это коммерческий слой в публичном
   контентном API. Оставляем, закрываем за сервис-токен или убираем?
7. **Авторизация интеграции.** Нужен ли отдельный сервис-токен и свой лимит
   частоты под коннектор (сейчас контент отдаётся анонимно)?
8. **Ключ.** Подтвердить, что `sku` подходит как сквозной идентификатор на их
   стороне (или нужен наш `id`/другой ключ).
9. **Частота и объёмы.** Ожидаемая частота синка, размер каталога, требования
   к latency — влияет на пагинацию/индексы/кэш.
10. **Версионирование контракта.** Нужна ли фиксированная версия схемы и
    политика её изменений (сейчас `VERSION: 1.0.0` в OpenAPI).

## Известные мелочи (не блокеры)

- `ProductDetailSerializer.get_group` делает отдельный запрос соседей по серии —
  это **не** построчный N+1: деталь отдаёт один товар, все связи префетчатся,
  «лишний» запрос один на запрос. При необходимости оптимизируется точечно.
- Публичная отдача `erp_code` — см. вопрос №6.

## Как посмотреть за 2 минуты

```bash
pip install -r requirements.txt      # добавлен drf-spectacular
python manage.py migrate
python manage.py runserver
# затем:
#   http://127.0.0.1:8000/api/docs/                     — Swagger UI (весь контракт)
#   http://127.0.0.1:8000/api/schema/                   — OpenAPI YAML
#   http://127.0.0.1:8000/api/products/by-sku/<sku>/    — карточка по ключу контента
#   http://127.0.0.1:8000/api/products/?updated_since=2026-06-01T00:00:00Z
```
